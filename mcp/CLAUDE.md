# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A containerized FastMCP server for the Radiant D.A.V.I.D agents. It provides:

1. `/health` + `/ready` HTTP endpoints for container orchestration (liveness only — no StarRocks probe).
2. Mandatory OAuth 2.1 (Keycloak/OIDC) authentication in front of the MCP endpoint.
3. Per-request JWT pass-through so each MCP tool call executes StarRocks queries **under the authenticated user's identity**. This component holds **no** StarRocks credentials — there is no static-credential fallback.

All tools live in `radiant_mcp/tools/` and are registered on the server's FastMCP instance by `register_tools()`. `describe_schema`, `bar_chart` and the raw SQL tools `read_query` / `table_overview` (the agents' last resort) are always registered. The **Radiant API tools** (`list_tenants`, `search_cases`, `get_case_context`, `search_patients`, `get_patient_context`, `prioritize_snv`, `case_cnv`, `variant_details`, `variant_carriers`, `second_hit`, `gene_info`, `lookup_terms`, `cohort_carriers`, `genotype_phenotype`, and the chart tools `family_venn`, `survival_curve`, `oncoprint`, `lollipop`, `patient_timeline`) are registered only when `RADIANT_API_URL` is set. They call the Radiant portal API through the generated `radiant_python` client, forwarding the caller's JWT as a Bearer token. They serve the three D.A.V.I.D agents (case, patient, cohort) of LibreChat; the agents' instructions are in `librechat-local/agent-radiant-*.md` (spec: hub `docs/features/RAD-251-david-agents.md`).

The server used to wrap the upstream `mcp-server-starrocks` package; RAD-259 replaced it with `starrocks.py` and `tools/query.py` (its global client had to be monkey-patched, and its `table_overview` cache served one user's rows to the next).

## Gotchas (read first)

- **Nothing is cached across callers.** Every StarRocks statement opens its own connection under the caller's JWT (`starrocks.py`), so StarRocks applies that user's grants each time. Never add a cache keyed only by query, table or gene: it would serve one user's rows to another.
- **API responses are read as raw JSON.** `portal_api.py` calls the generated client's `*_without_preload_content` methods and parses the body itself: the generated response models mark many fields required and non-null, so one NULL in the data would fail the whole call. Request bodies still use the generated models. Nested SQON bodies must be built from the model classes (`Sqon`, `SqonContent(actual_instance=...)`, `LeafContent`): the generated `from_dict` cannot deserialize nested `oneOf` lists.
- **Curated SQL binds named parameters.** `second_hit`, `gene_info`, `cohort_carriers`, `genotype_phenotype` and the charts (`family_venn`, `oncoprint`, `lollipop`, the carrier groups and patient lists of `survival_curve`) have no portal endpoint: they run fixed queries in StarRocks under the caller's JWT (`sql.py`, through `starrocks.query(token, sql, params)`). Values go through `_sql.Params`, which returns named placeholders (`%(p0)s`) so the binding never depends on the order fragments are built (a positional version swapped the gene and the tenant). Values are also validated first (`_sql.symbol`, `tenant_db`, `hpo_id`, closed lists); only the validated tenant database name is written into the SQL. They also read four portal-owned views of the tenant database: `interpretation_germline`, `obs_categorical`, `gene_panel_mv`, and `v_pcx_30_patient_list` (`queries/patients.py`: the portal's `search_patients` as one statement, so a survival cohort is one query instead of pages of 100; its virtual `age_at_initial_dx_group` mirrors `ageAtInitialDxGroupSQL` of the portal's `pcx_patients.go`: keep them equal by hand, CI does not check out that file; `tests/unit/test_patient_list.py` fails when the portal's array filter fields change). The clinical rules (rarity, P/LP sources, CNV types) live in `domain/rules.py` (spec: hub `docs/features/RAD-252-david-p2-tools.md`).
- **FastMCP publishes only part of a docstring.** The tool description is the text before `Args:`; anything after the block (a `Returns ...` paragraph, `Note:`) is dropped, and an entry like `case_id, seq_id, task_id: ...` documents none of the three. Put everything the agent must know before `Args:` and give each argument its own entry. `test_the_assistant_sees_every_line_of_each_tool_docstring` (`tests/unit/test_registration.py`) fails otherwise.
- **Portal links are a boundary.** `portal_links.py` mirrors the portal frontend routes (`/{tenant}/case/entity/{id}`, `/{tenant}/patient/entity/{patient_key}`, `/{tenant}/variants/entity/{locus_id}`) and the case variants tab parameters (`tab`, `seq_id`, `task_id`, `variant_section`, `selectedVariant`). When the portal renames one, update the module and its tests. The model must never build a URL itself: every tool returns `portal_url` (only when `RADIANT_PORTAL_URL` is set).
- **`describe_schema` mirrors the ETL schema.** `schema_catalog.py` (tables, columns, partitions, example queries) and `enums.py` (stored, case-sensitive values) are checked by `tests/unit/test_schema_catalog.py` against the ETL's create-table DDL and data QA dictionaries (`RADIANT_ETL_DIR`, or a sibling `etl` / `radiant-portal-pipeline` checkout). CI checks out ETL `main`, so an ETL schema change that breaks the catalog fails here.
- **The curated SQL is checked against the schema too.** `tests/unit/test_curated_sql_schema.py` calls every `*_query` builder of `radiant_mcp/queries/` with sample arguments, parses the SQL with sqlglot (dev dependency) and resolves every table and column against what the ETL creates and what the portal creates in a tenant database: the `v_pcx_30_*` views, one view per PostgreSQL table of `types.ViewTables` (columns replayed from `backend/scripts/init-sql/migrations`) and `gene_panel_mv`. The sources are read by `tests/unit/schema_sources.py`. A new builder must be added to `_queries()` (`test_every_builder_is_covered` fails otherwise).
- **OAuth is mandatory.** `KEYCLOAK_REALM_URL` is required — `__main__.py` raises `SystemExit` at startup if it is unset. There is no non-OAuth path anymore (removed 2026-07-24), and the container is never given StarRocks credentials.
- **One provider, both client paths.** `__main__.py` uses fastmcp's native `KeycloakAuthProvider` — a pure JWT resource server (holds no client secret, mints no tokens). It just validates incoming Bearer JWTs against Keycloak's JWKS. Self-discovering clients (Claude Desktop) get tokens via Keycloak's own DCR + PKCE; portal clients (LibreChat) present a raw Keycloak token directly. Both hit the same verifier, so there is **no** `MultiAuth`/fallback-verifier and no server-side token swap. (This replaced an earlier `OIDCProxy` + `MultiAuth` hand-rolled setup — see git history if you need the rationale.)
- **`KeycloakAuthProvider` needs Keycloak ≥ 26.6.0** for the DCR path (keycloak PR #45309). The portal/direct-token path works on any version. It fetches Keycloak's JWKS at startup, so the server hard-fails to boot if Keycloak isn't reachable — hence `radiant-mcp` depends on `keycloak: service_healthy` (see the healthcheck note below).
- **Audience is optional and intentionally unset.** StarRocks' `authentication_jwt` only checks `aud` when the user is created `WITH ... required_audience`, which we don't do. Setting `KEYCLOAK_AUDIENCE` would make the provider *require* that `aud` on every token — which DCR-registered clients (their own client_id, no audience mapper) don't carry — so leave it unset unless you also add a matching audience mapper on a default client scope.
- **Every query has a timeout and `read_query` a row cap.** `STARROCKS_QUERY_TIMEOUT` (seconds, default 60) is set as the session `query_timeout`, and the socket read timeout is 5 s longer. `read_query` reads at most `STARROCKS_MAX_ROWS` (default 500) rows plus one and returns `truncated: true` when more exist, so a `SELECT *` on an occurrence table cannot load millions of rows into the shared process. Its session also sets `sql_select_limit` to that number: closing the connection would otherwise read and discard the rest of the result (an explicit `LIMIT` in the statement still wins). StarRocks runs every statement of a multi-statement call (it ignores the client's MULTI_STATEMENTS flag): `query()` skips the leading statements without a result (`USE`, `SET`), returns the first result set, raises an error from any statement, and `read_query` warns when later statements returned rows it does not show.
- **Germline SNV calls follow the platform's carrier rule.** `queries/quality.py` `germline_qualifies` = FILTER PASS, GQ >= 20, alt depth >= 3 (`rules.GERMLINE_MIN_*`), the ETL's `qualifies` in `germline_snv_staging_variant_freq_insert.sql`, so cohort counts match the portal's variant frequencies. Carrier tools (`carriers_cte`) and germline `oncoprint` filter on it; `second_hit` keeps such calls and marks them `low_quality` (a poorly covered real hit stays visible). `filter` is per site and `gq` per sample: PASS alone would keep a poor parent call in a trio. `family_venn` does not apply it. Keep the thresholds equal to the ETL's. Somatic SNV carriers follow the ETL's somatic `qualifies` (`somatic_snv_staging_variant_freq_insert.sql`): `somatic_qualifies` = FILTER PASS, tumor alt depth >= 2 (`rules.SOMATIC_MIN_TUMOR_AD_ALT`), in `carriers_cte` and somatic `oncoprint`; the somatic `second_hit` keeps the PASS calls that fail it, marked `low_quality` (as the germline ones).
- **Genes are resolved by symbol, not alias.** `services.genes.resolve_gene` / `resolve_genes` call the portal gene search (one call for a list of names: oncoprint, the survival groups), which matches the HGNC symbol and the Ensembl gene id only (`SearchGenes` does not read `ensembl_gene.alias`): HER2 or P53 are not found. Tool descriptions say so, and `not_found_message` tells the agent to retry with the official symbol. Drop that rule once the portal matches aliases.
- **Timeouts are per statement, not per call.** `STARROCKS_QUERY_TIMEOUT` and `RADIANT_API_TIMEOUT` bound one statement or one request; a tool chains several (`cohort_carriers`: 2 API calls, up to 5 statements). The MCP client's timeout must be well above them (LibreChat QA: `timeout: 180000` on the `radiant` server), or the client cuts the call first and the agent never sees StarRocks' timeout message.
- **StarRocks re-validates the JWT itself.** A working token isn't enough — a StarRocks user whose name is the token's `sub` (UUID) must exist as `IDENTIFIED WITH authentication_jwt` (with `principal_field: sub`), and StarRocks needs SSL enabled for JWT auth.
- **Radiant API tools are opt-in.** `register_tools()` registers only `describe_schema`, `bar_chart`, `read_query` and `table_overview` unless `RADIANT_API_URL` is set, so the compose stack (which has no Radiant API) still boots. The `radiant_python` client is a generated OpenAPI package installed from git and pinned to a commit SHA (the `radiant-python-cli` git URL in `pyproject.toml`) — bumping it can change model fields/method names. It is a sync urllib3 client, so tool bodies run on worker threads (`workers.run`); the JWT is read from the contextvar *before* hopping threads. The client does not retry (`configuration.retries = False`: urllib3 would retry a GET 3 times, each with a fresh timeout) and has a short connect timeout; a timeout or a refused connection maps to `upstream`.
- **Unit tests and lint run in CI, integration tests do not.** `.github/workflows/test.yml` runs `ruff check` (rules in `pyproject.toml`, ruff pinned in the dev group) and the pytest suite (`tests/unit/`, fake portal API, no network). The shell integration suite needs Docker and is run by hand.

## Commands

```bash
# Build the image
docker build -t radiant-mcp:latest .

# Bring up the full stack (keycloak + starrocks + radiant-mcp)
docker compose up --build

# Run the unit tests (no Docker). Point RADIANT_ETL_DIR / RADIANT_PORTAL_DIR at the
# ETL and portal checkouts (on main) to include the schema checks; without them they
# are skipped.
uv sync && RADIANT_ETL_DIR=../radiant-portal-pipeline RADIANT_PORTAL_DIR=../radiant-portal uv run pytest

# Lint (CI fails on any alert; --fix applies the safe fixes)
uv run ruff check .

# Run the integration test suite (6 tests, requires Docker)
docker compose --profile test run --rm test-runner

# Run the integration test against an already-running stack, from the host
KEYCLOAK_URL=http://localhost:8080 MCP_URL=http://localhost:8000 \
  ./tests/integration/test-oauth-flow.sh

# Regenerate the self-signed StarRocks FE keystore (only if tls/starrocks.jks is missing)
./tests/integration/gen-starrocks-keystore.sh
```

The unit tests replace the HTTP client with a fake (`tests/unit/conftest.py`, `FakeApi`), the curated SQL with `FakeSql`, and the MySQL connector with a fake server in `tests/unit/test_starrocks.py`. The integration tests are shell-based: to run a single assertion, edit/comment blocks in `tests/integration/test-oauth-flow.sh` (tests are numbered sequential `curl` blocks, not independently selectable).

## Architecture

### Request flow

```
MCP client → KeycloakAuthProvider (validates JWT via Keycloak JWKS) → MCP tool
          → starrocks.query() → per-request MySQL conn to StarRocks (JWT auth)
StarRocks re-validates the same JWT against Keycloak's JWKS and runs the query as that user.
```

Keycloak is the IdP for **both** hops: it issues the token to the client, and StarRocks independently verifies that same token. The `radiant-mcp` service holds **no** StarRocks credential — a tool call without a JWT is rejected, not run as a shared user. `/health` is liveness-only and never touches StarRocks.

### Module layout (`radiant_mcp/`)

- `__main__.py` — entrypoint. Parses args, **requires** `KEYCLOAK_REALM_URL` (raises `SystemExit` if unset), creates the `FastMCP` instance, configures `KeycloakAuthProvider` (set as `mcp.auth`), registers the tools, then starts uvicorn.
- `app.py` — Starlette factory. Mounts the MCP ASGI app at `/mcp`, adds `/health`, `/ready`, and the `.well-known` OAuth routes; CORS open to every origin, without credentials (bearer tokens only). Uses the MCP app's own `lifespan`.
- `starrocks.py` — StarRocks access under the caller's JWT: `connect(token, database)` and `query(token, sql, params, database=, max_rows=)`. See below.
- `oauth.py` — hand-rolled RFC 9728 protected-resource metadata endpoint (workaround, see below). Advertises the Keycloak realm as the authorization server.
- `health.py` — unauthenticated liveness/readiness handlers (no StarRocks probe).
- `settings.py` — every environment variable, as one pydantic-settings `Settings` model: typed, validated, read once. `__main__` calls `load_or_exit()` first, so a missing `KEYCLOAK_REALM_URL` or a malformed value (a non-numeric port, a bad database name) stops the server with one line per variable. Modules call `get_settings()`, never `os.getenv` (the one exception is `MPLCONFIGDIR`, set for matplotlib before its import). Tests install their own instance through the autouse `configure` fixture of `tests/unit/conftest.py`, which ignores the developer's environment.
- `portal_links.py` — builds the `portal_url` of cases, occurrences, patients and variants from `RADIANT_PORTAL_URL`.
- `enums.py` — stored values of the enum columns; `canonical_values()` maps filter values onto them case-insensitively (StarRocks compares case-sensitively).
- `schema_catalog.py` — the curated tables, rules and example queries rendered by `describe_schema`.
Layers, each importing only from the ones above it in this list: plumbing → `domain/` → `queries/` → `services/` → `tools/`. A tool module never imports another tool module. `schema_catalog.py` reads `domain.rules` (the nearby consequences), so it sits above `domain/`, like `services/`.

- `api_fields.py` — the fields each portal search endpoint can filter or sort on (cases, patients, the four occurrence lists), mirroring `CanBeFiltered` / `CanBeSorted` of the backend field lists. The backend silently drops a sort on an unsortable field, and its default sort with it, so the tools reject such a field. `tests/unit/test_api_fields.py` compares them with `backend/internal/types` of the portal checkout: regenerate them when it fails.
- `results.py` — the one result shape of every tool, `ToolOutput`: `ok`, `data` (the tool's own fields), `warnings` (always a list), `truncated` (`reason`, and `lists` when several lists can be cut), `error` (`code` among `ErrorCode`, `message`, `details` such as `allowed` values or the API `status` / `body`) and `portal_url`. Tool bodies return `ok(...)` or raise `ToolFailure` (`invalid()`, `not_found()`); `failure(exc)` maps any exception to an error (API 400/422 → `invalid_input`, 401 → `auth_required`, 403 → `forbidden`, 404 → `not_found`, other → `upstream`; StarRocks access denied → `forbidden`, a token past its `exp` → `auth_required` (checked before each StarRocks connection: a tool chains statements for minutes, and StarRocks would deny the expired login as a missing grant), other StarRocks errors → `upstream`, except a statement `read_query` sent that StarRocks cannot parse or analyse → `invalid_input` (`StarRocksError.kind`, from the message: StarRocks reports many errors, timeouts included, as 1064); `InvalidInput` → `invalid_input` with its `details` (`one_of` adds `allowed`); anything unexpected → `internal`, its message logged, never returned). What the agent never gets: a StarRocks connection error (host, port, TLS) and a portal 5xx body are logged and replaced by a short message (5xx keep `status` and `correlation_id`; 4xx keep their `body`); a StarRocks error is logged with its kind and number only, its message (which can quote the statement) at DEBUG. `respond()` builds the MCP result: the JSON text, the same object as structured content, the chart PNG as an image part and `isError` on failures. `register_tools` publishes `OUTPUT_SCHEMA` as every tool's output schema and installs `ArgumentErrors`, which turns the arguments FastMCP rejects before the tool runs (a `Literal` outside its list, a pydantic model such as survival's `GroupSpec`) into the same envelope (`invalid_input`, `details.errors`, `details.allowed`) instead of FastMCP's raw pydantic text; `tests/unit/test_tool_calls.py` calls tools through a FastMCP `Client`; `tests/unit/test_results.py` checks the contract.
- `call_log.py` — `CallLog` middleware (added in `__main__`): one INFO line per tool call on the `radiant_mcp.calls` logger, `tool=… sub=… ms=… outcome=ok|<error code>`. No argument and no result is logged: they can hold patient identifiers.
- `workers.py` — the worker threads shared by all callers: `run(fn)` admits at most `MCP_MAX_CONCURRENT_CALLS` tool bodies at once and fails with `upstream` ("busy") after `MCP_QUEUE_TIMEOUT` seconds instead of queueing behind slow calls. Every tool body goes through it (`portal_api.run`, `tools/query._run`, `bar_chart`).
- `portal_api.py` — portal API plumbing: `run()` reads the JWT on the event loop, then runs the tool body on a worker thread with a `RadiantApi` (`call(api, operation, **kwargs)` → JSON) and turns its `ToolOutput` or exception into the MCP result; `resolve_tenant` (raises `ambiguous_tenant` with `details.tenants`); `RADIANT_API_TIMEOUT`; `SEARCH_MAX_LIMIT`. Imported as `_api`.
- `sql.py` — curated SQL plumbing: input validation, named bound parameters (`Params`), `run()` through `starrocks.query`, row normalization (`as_list` for ARRAY columns, which StarRocks sends as JSON text), and `cut(rows, limit)`: the queries read `limit` + 1 rows and `cut` tells a cut list from a complete one of exactly `limit` rows; every capped list goes through it. Imported as `_sql`.
- `domain/` — no I/O. `data_types.py`: the one data_type vocabulary (`Literal` types annotate the tool arguments, so the agent sees the allowed values): case tools take the portal's `somatic_snv_tn` / `somatic_snv_to`, cohort and chart tools `somatic_snv_tn` only (`latest_tasks` keeps the somatic tasks with a normal sample: a tumor-only analysis keeps the germline variants, about 95 % of its calls per the ETL's SJRA-1751 design, and would count polymorphisms as somatic carriers); `somatic_snv` is accepted nowhere. `keys.py`: `variant_part()`. `rules.py`: the clinical rules of the RAD-252 tools. `consequences.py`: VEP consequence classes. `criteria.py`: `Criteria` / `build_criteria` of the carrier tools.
- `queries/` — every SQL builder (`*_query`, returning `(sql, Params)`): `sequencing.py` (the one join to `staging_sequencing_experiment`, `parts_query`), `hits.py`, `carriers.py` (`carriers_cte` and the cohort, lollipop and survival carrier queries), `charts.py` (Venn, oncoprint), `genes.py`, `patients.py` (the clinical patient list of `survival_curve`).
- `services/` — what several tools share: `cases.py` (case context, `lookup_parts`, `search_criteria`), `patients.py` (patient context, `no_clinical_data`, `PATIENT_KEY`, patient filter fields), `genes.py` (`resolve_gene`).
- `tools/__init__.py` — `register_tools(mcp)`.
- `tools/patients.py` — `search_patients` and `get_patient_context` (patient page endpoints, backed by the tenant's secured `v_pcx_30_*` views). A 404 without the API's JSON error body (patient routes not registered, `PATIENT_VIEW_ENABLED` off) or a 500 (the tenant's views missing; a 502/503/504 is an outage and stays `upstream`) fails with the `unavailable` error code (`services.patients.no_clinical_data`), not a generic API error. Sections load concurrently (3 workers, under the backend's per-user StarRocks pool).
- `tools/occurrences.py` — `prioritize_snv` and `case_cnv`: the case variants tab's list and count endpoints with a SQON built from `{field, op, value}` filters (enum values canonicalized); the backend validates field names.
- `tools/variants.py` — `variant_details` (variant page endpoints, plus the expanded occurrence when a key is given; transcripts trimmed to MANE / canonical / picked) and `variant_carriers` (interpreted and uninterpreted cases).
- `tools/schema.py` — `describe_schema(topic)`.
- `tools/query.py` — `read_query(query, db)` (row cap, `truncated`) and `table_overview(table)` (row count, `DESCRIBE`, 3 sample rows; database and table names validated, never cached).
- `tools/hits.py` — `second_hit`: germline SNV + LOSS CNV on the same gene and compound heterozygous pairs per sequencing; somatic: the patient's germline P/LP variants (germline sequencing found in `staging_sequencing_experiment`) + somatic SNV (tumor-normal analyses only; a tumor-only analysis is skipped with a warning) or LOSS/CNLOH CNV (from the tumor-only CNV calling, the only somatic CNV source) in the same gene; a tumor-normal call of the germline first-hit locus goes to `germline_variant_in_tumor`, never counted, with `possible_allelic_imbalance` when the germline call is HET and the tumor ratio is >= `rules.ALLELIC_IMBALANCE_MIN_RATIO` (purity unknown: a flag, not a hit). Its `vep_impact` is the most severe impact on the reported gene (a window in the query, `_impact_on_gene`, so the row cap counts variants; the compound heterozygous pairs read it from the consequences too, an unknown impact stays NULL); `aa_change` and `picked_vep_impact` describe the picked transcript (HGVSg is genomic). Every occurrence query filters on its key's `part`.
- `tools/cohort.py` — `cohort_carriers` and `genotype_phenotype`: the gene selects the variants with a consequence on one of its transcripts (`radiant.snv__consequence_filter`, so overlapping genes count; a `vep_impact` filter keeps a variant by its most severe impact on that gene (`queries.impact.most_severe_in`); a `clinvar` filter, like the P/LP test of `second_hit`, counts for the gene only when it is the variant's picked gene or its impact there is at least LOW (`rules.PLP_GENE_IMPACTS`): a classification belongs to the variant, not to a nested or overlapping gene; an upstream, downstream or intergenic consequence does not count, `rules.NEARBY_CONSEQUENCES`: VEP reports every gene within 5 kb; `second_hit` and `oncoprint` apply the same rule) or the CNVs whose gene array holds it; occurrences are joined on `locus_id` in `snv__variant` and mapped to case and patient through `staging_sequencing_experiment`, keeping only the latest task of each (case, sequencing) among the imported tasks (`ingested_at` past the ETL's epoch placeholder) of the type that feeds the data type (`queries.sequencing.latest_tasks`, also used by `oncoprint`): a re-analysis leaves the old task's occurrences in place, and tumor-normal and tumor-only somatic tasks share a type but are told apart by a normal sample, like the portal's `somaticCohortCounts`; `cases` counts the cases whose proband carries (a relative's sequencing carries the proband's `case_id`), like `oncoprint`; `cases_any_member` counts any carrier member, and `summary.by_family_role` splits them; phenotypes come from `obs_categorical` (`phenotype`, `positive`), without fetal observations (a fetal sample carries its mother's `patient_id`).
- `charts.py` — chart rendering (RAD-254): pure functions, headless matplotlib (`Agg`), PNG kept under 1 MB, one chart at a time (`_RENDER_LOCK`: pyplot keeps global state and tools run on worker threads). Survival statistics: `scipy.stats.ecdf` on right-censored data (Kaplan-Meier) and a vectorized k-sample log-rank test (pseudo-inverse of the variance matrix, df = its rank, so a group with nobody at risk at the death times drops out), computed before taking `_RENDER_LOCK`; mathtext is off (`text.parse_math`), so a `$` in agent or portal text stays a dollar sign; a unit test checks them against the Freireich 1963 example (medians 23 / 8 weeks, p = 4.17e-5). SciPy rather than lifelines: lifelines pins pandas < 3.
- `tools/charts/` — one module per chart: `venn.py` (`family_venn`), `survival.py` (`survival_curve`; its `groups` are the pydantic `GroupSpec` model, so the agent gets their exact schema; with a carriers group, `sequenced_only` keeps the patients with an imported analysis of its data type, `queries.sequencing.genotyped_patients_query`, not any Radiant case), `oncoprint.py`, `lollipop.py`, `timeline.py` (`patient_timeline`), `bar.py` (`bar_chart`). Each returns the common result with the values drawn in `data` and the PNG as an image part after the JSON text (`ok(..., image=png)`), which LibreChat saves as a message attachment and shows; a chart with nothing to draw returns `ok` with a warning and no image. Venn counts only occurrences with an alternate allele (`HET`/`HOM`/`HEM`); the ETL loads only those (`has_alt`), so the filter is a safeguard. Survival reads each patient list in one statement on `v_pcx_30_patient_list` (`queries/patients.py`, capped at 50000 in patient key order, reported as `truncated`); it reads the view directly, so the portal's gates on its patient routes (`can_search_case`, `PATIENT_VIEW_ENABLED`) do not apply: the view masks the PHI columns by the caller's rights but filters no row, so a caller without `can_search_case` still gets de-identified survival per group, as with `read_query` on the same views (StarRocks/Ranger grants are the barrier; restrict with a Ranger policy on `v_pcx_*` if needed); the cohort and group filter sets are AND-ed, never merged (merging intersects the values of an array field such as `chemotherapy_agents`); carrier genes are resolved before any list is read; without a carriers group, `sequenced_only` keeps patients with a Radiant case (`case_count`); `deceased` is the event, `survival_days` the time. Charts label cases by id, never by name or MRN. `bar_chart` needs no API and is always registered.
- `tools/genes.py` — `gene_info` (gene resolved by the portal gene search, panels and gnomAD constraint by SQL) and `lookup_terms` (HPO / MONDO autocomplete).
- `services/cases.py` + `tools/cases.py` — `get_case_context(case_id, tenant=None)` (`services.cases.case_context`) composes `CasesApi.case_entity` + `case_tasks_with_occurrences` (one call per non-deprecated `data_type`, chosen from `case_type`) into a single payload ending with `occurrence_keys` = `(case_id, seq_id, task_id, data_type)` tuples for follow-up variant queries. Each key also carries `part` / `variant_part` (`domain.keys.variant_part` = `part // 10`, mirroring `compute_part` in the pipeline's `import_part.py`): the StarRocks occurrence tables, `exomiser` and `radiant.snv__consequence_filter_partitioned` are `PARTITION BY (part)`, `snv__variant_partitioned` by `variant_part`. **Temporary:** `part` is resolved by `services.cases.lookup_parts()` with a StarRocks query on `<RADIANT_SHARED_DB>.staging_sequencing_experiment` through `_sql.run` (the caller's JWT, passed explicitly because the body runs on a worker thread) — to be removed once the Radiant API returns `part` per task. A failed lookup adds a `warnings` entry, it never fails the tool. A task the ETL has not imported yet (`ingested_at` at its epoch placeholder) gets no `part` and `imported: false`, so `second_hit` and `family_venn` read the loaded task of a re-analysis instead. Tenant discovery uses `AuthApi.get_me()`: one membership → auto-selected, several → error listing them. `list_tenants` exposes the same list. `search_cases(filters, query, ...)` wraps `CasesApi.search_cases` (criteria are AND-ed, default operator `in`; the filterable/sortable aliases come from `api_fields.py`) and, for `query`, resolves the prefix via `autocomplete_cases` then runs one search per matched id type and merges — the API has no OR across fields. Autocomplete types `case_id` / `patient_id` / `sequencing_experiment_id` / `proband_submitter_sample_ids` map to the same-named filters; any other type is a `submitter_patient_id_type` (e.g. `mrn`) and goes through the `mrn` filter (alias of `patient.submitter_patient_id`). A user filter on the same field as a match is intersected with it (`services.cases.merge_criteria`), never overwritten.
- `server.py` (repo root) — thin shim (`asyncio.run(main())`) kept as the Docker `CMD`.

### starrocks.py — the core mechanism

`starrocks.query(token, sql, ...)` runs every StarRocks statement of the server, from `read_query`, `table_overview` and the curated SQL (`_sql.run`). On each call it:

1. Fails with `StarRocksError("Authentication required: no JWT in request context")` when there is **no token**. There is **no** static-credential fallback and no pool.
2. Writes the token to a `0o600` temp file, opens a **one-shot** `mysql.connector` connection with `auth_plugin='authentication_openid_connect_client'` + `openid_token_file`, and removes the file once connected. Host, port and default database come from `STARROCKS_HOST` / `STARROCKS_PORT` / `STARROCKS_DB` (connection targets, not credentials).
3. Sets the session `query_timeout` (`init_command`) and a socket `read_timeout`, runs the statement with bound parameters, reads the first result set (at most `max_rows + 1` rows when a cap is given), and closes the connection in `finally`.

The caller reads the JWT from the MCP auth context **on the event loop** (`_api.get_jwt_token()`) and passes it down, because tool bodies run on worker threads. The username sent to StarRocks is the JWT's `sub` claim, decoded **without signature verification** — verification already happened in `KeycloakAuthProvider`, and StarRocks verifies the token again. A StarRocks user named that `sub` (UUID) must exist and be `IDENTIFIED WITH authentication_jwt` (`principal_field: sub`). Database and table names written into a statement go through `starrocks.database_name()` (`[A-Za-z0-9_]`).

### OAuth is mandatory

`__main__.py` requires `KEYCLOAK_REALM_URL` and raises `SystemExit("KEYCLOAK_REALM_URL is required")` if it is unset — there is no static-credential path. `mcp.auth` is always a single `KeycloakAuthProvider(realm_url=..., base_url=..., audience=None, required_scopes=[...])`. It is a `RemoteAuthProvider` subclass that builds a JWKS `JWTVerifier` internally (issuer = `realm_url`, `jwks_uri = {realm_url}/protocol/openid-connect/certs`, RS256). It validates any valid Keycloak JWT regardless of how the client obtained it:
- **Self-discovering clients** (Claude Desktop) run OIDC discovery, register via Keycloak's DCR, and do the auth-code + PKCE browser flow — all against Keycloak directly. The server only advertises Keycloak as the authorization server.
- **Portal clients** (LibreChat) already hold a Keycloak token and present it as a Bearer.

In **both** paths the resulting `AccessToken.token` is a real Keycloak JWT, which `starrocks.py` forwards to StarRocks — so the per-user pass-through works regardless of how the client authenticated. No `MultiAuth`, no token swap, no server-held client secret.

### Why oauth.py exists (workaround)

FastMCP serves protected-resource metadata under `/mcp/.well-known/...` and Pydantic's URL serialization appends trailing slashes that some MCP clients reject on strict comparison. `oauth.py` + the extra routes in `app.py` re-serve RFC 9728 protected-resource metadata at the canonical root paths with clean URLs, advertising the Keycloak realm as the authorization server. Authorization-server metadata (RFC 8414) is **not** served by us — the native provider points clients straight at Keycloak for that. If clients start failing OAuth discovery, this is the first place to look.

## Docker notes

- Multi-stage build: `uv`-built venv in the builder stage is copied into a slim runtime; deps are declared in `pyproject.toml` and installed with `uv sync --frozen` from `uv.lock`, so versions only change when someone runs `uv lock` and commits the diff.
- `COPY src/ dest/` with multiple sources flattens files. Copy files and directories on **separate** `COPY` lines (see `Dockerfile`).
- The compose `starrocks` service appends `fe-ssl.conf` to `fe.conf` before boot and mounts a JKS keystore to enable TLS — required because StarRocks JWT auth needs SSL. `starrocks-init` then seeds `test_db` and creates the `testuser` JWT user.
- `keycloak` has a healthcheck that probes `:9000/health/ready` over a raw bash `/dev/tcp` socket (the keycloak:26 image has bash but no curl/wget) and matches the HTTP `200` status line. `radiant-mcp` waits on `keycloak: service_healthy` because `KeycloakAuthProvider` fetches the JWKS at startup (above).
- Run the tests with `docker compose --profile test run --rm test-runner`, **not** `up --abort-on-container-exit` — the one-shot `starrocks-init` exits 0 on success, which trips `--abort-on-container-exit` and tears the stack down before the test runs.

## Environment variables

Connection **target** (no credentials): `STARROCKS_HOST`, `STARROCKS_PORT` (9030), `STARROCKS_DB`, `STARROCKS_CONNECTION_TIMEOUT` (seconds, default 10). There is intentionally **no** `STARROCKS_USER` / `STARROCKS_PASSWORD` — access is per-user via JWT. Limits: `STARROCKS_QUERY_TIMEOUT` (seconds, default 60), `STARROCKS_MAX_ROWS` (rows returned by `read_query`, default 500). TLS: `STARROCKS_SSL_VERIFY` (default false) checks the FE certificate chain and hostname against `STARROCKS_SSL_CA` (a PEM file) or, unset, the system CA bundle. The connector's C extension does not load the system store itself, so `settings.system_ca_bundle()` passes the bundle as `ssl_ca`. The local compose stack has a self-signed keystore and leaves verification off.

Radiant API (optional): `RADIANT_API_URL` — base URL of the Radiant portal API; enables the Radiant API tools. No API credential: the caller's JWT is forwarded. `RADIANT_API_TIMEOUT` (seconds, default 60) — read timeout of each request; `RADIANT_API_CONNECT_TIMEOUT` (default 5). `RADIANT_PORTAL_URL` — portal base URL; when set, tools return a `portal_url` for every case, patient, occurrence and variant. `RADIANT_SHARED_DB` (default `radiant`) — StarRocks database holding the shared tables: every curated query reads them there, and `describe_schema` names it in place of `radiant.`.

OAuth (required): `KEYCLOAK_REALM_URL` (bare realm URL, e.g. `http://keycloak:8080/realms/radiant`) — the server refuses to boot without it; `MCP_BASE_URL` (server **root**, not `/mcp`), `OAUTH_REQUIRED_SCOPES` (comma-separated, default `openid`), `KEYCLOAK_AUDIENCE` (optional; leave unset — see the audience gotcha above), `OAUTH_SUPPORTED_SCOPES` (comma-separated, default `openid,offline_access`; advertised in the protected-resource metadata). The server needs no client id/secret.

Concurrency: `MCP_MAX_CONCURRENT_CALLS` (default 20) tool bodies at once for all callers; `MCP_QUEUE_TIMEOUT` (seconds, default 10) before a waiting call fails as busy. The cap counts calls, not connections: `gene_info`, `variant_details`, `get_patient_context`, the task lookups of `case_context` and the `cohort_carriers` summaries fan out to 3 threads inside their slot, so StarRocks and the portal can see up to 3x the cap.

Proxy: `FORWARDED_ALLOW_IPS` (default `*`) — the proxies whose `X-Forwarded-*` headers uvicorn trusts.

All of them are fields of `settings.Settings`: add a new variable there, never as an `os.getenv` in a module.
